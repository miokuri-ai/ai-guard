# 指示文3: 規則の棚卸し(数を減らす)

いつ使うか: 教訓メモや規則のファイルが増え、作業の瞬間に「今どの規則が当てはまるか」を思い出せなくなってきたとき。目安として、規則が数十件を超えたら。

考え方: 規則は、増やすほど守られなくなる。失敗のたびに文章の規則を足すのをやめ、次の4つに仕分ける。
1. **仕組みで守れているもの** → 文章からは消す(仕組みの場所だけを書いた1行を残す)
2. **仕組みにできるもの** → 仕組みにする仕事を発注し、できたら1へ
3. **判断の基準として残すもの**(機械では判定できない、人やAIの判断が要るもの) → 残す。ただし数を絞る
4. **もう要らないもの**(前提が変わった、別の規則と重複している) → 消す

---

```
このプロジェクトの規則を棚卸しします。規則を足すのではなく、仕分けて減らすのが目的です。

# 対象
{規則・教訓メモ・注意事項の置き場所}

# 仕組みの置き場所(すでに強制しているもの)
{例: フックの設定、メモリの上限の仕組み、データ期間の封印、テスト}

# やること
1. 規則を1件ずつ、次のどれかに仕分ける
   A. 仕組みで守れている(どの仕組みかを書く)
   B. 仕組みにできる(どう仕組みにするかを1〜2行で)
   C. 判断の基準として残す(機械で判定できない理由を書く)
   D. 要らない(前提が変わった/重複している、のどちらかと、その根拠)
2. 同じことを言っている規則は1つにまとめる候補として挙げる
3. その規則ができたきっかけ(事故・失敗)が分かれば添える

# 出してほしいもの
- 仕分けの一覧(規則の場所、A〜D、理由)
- C(残す)の件数。多すぎる場合は、さらに絞る案
- B(仕組みにできる)の、優先順位つきの一覧

規則の削除や書き換えは、まだしないでください。一覧を人間が確かめてから行います。
```

---

使うときの注意:
- 消すのは、人間が一覧を確かめてから。消した規則の文面は、別の場所に保管しておく(なぜ消したかを含めて)
- C(判断の基準)は、役割ごとの定義ファイルに入れる。全員が読む場所に全部を置かない
- 公式の案内(Claude Code のベストプラクティス)も、例外を許さない規則はフックなどの仕組みに置き、規則のファイルの中身は少数に保つよう勧めている
